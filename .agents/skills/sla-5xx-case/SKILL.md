# 日度 5xx 故障分析与 case

从 Dynamo 仓库根目录执行。以用户指定的业务日、模型和范围为准。未指定模型时先统计日报内全部模型，再按 5xx 条数、失败率和是否跨模型集中决定追查范围。日报生成、口径修改和发布走 [sla-daily-report](../sla-daily-report/SKILL.md)。

## 从日报定位主要问题

1. 从 `learning/daily-report/YYYY-MM-DD/index.html` 的 `report-data` 提取路由、总日志条目及状态码。用以下命令快速对账。缺日报时，按 [日报方案](../../../learning/daily-report/report.md) 的现行筛选条件只读查询 Loki，在 case 中记录实际覆盖范围。

   ```bash
   python3 .agents/skills/sla-5xx-case/scripts/summarize_5xx.py YYYY-MM-DD
   ```

2. 使用北京时间 00:00 至次日 00:00 的左闭右开窗口。Higress 按访问日志条目计数，沿用该日报的域名、路由、方法、路径和其他过滤条件。5xx 率写明分母。全天全部匹配日志中的 5xx 占比、以 2xx/3xx/5xx 为分母的请求可用率、历史日报的 HTTP 2xx 达成率各自保留原口径。
3. 按模型、状态码、响应详情、上游及时间分布拆解。对高峰同时计算条数和同窗口失败率。保留有独立影响的异常，例如多个模型在同一 Pod 重启附近同时出现 503。查询缺测或范围不一致时写明原因与覆盖。

## 沿故障链路取证

按 [取证参考](references/evidence.md) 使用已授权的只读数据源。

- 上游返回的 5xx 先追 LiteLLM 的模型组、部署 ID 和错误详情，再用历史调用与 Controller 日志核对作业和地址。比较同组其他部署及缓存命中、重试、回退。当前地址用于描述当前状态，历史归因使用故障时的证据。
- 网关连接中断或超时，按上游 Pod 和时间聚类，查看重启前日志、容器退出时间以及探针或事件。固定的耗时台阶可定位调查范围，具体计时器、退出触发原因和底层故障需要额外证据。
- 以能核验的请求 ID 逐条关联。仅有时间、路由或相似计数时，将其作为交叉证据并说明匹配粒度。把已证实的故障链路、推断与待确认项写清楚。

## 归类并选出主要原因

先按证据为每条独立故障链路标注主类别，再按当天受影响的网关 5xx 条数降序列出最多三项主要原因。证据只支持一项或两项时按实际列出。条数接近时可结合失败率、持续时间和跨模型影响排序。无法可靠量化时，标明已观测数量的范围或关联粒度。

| 类别 | 适用证据 |
|---|---|
| 作业发布 | 作业发布、滚动更新、迁移、回滚或就绪检查异常直接导致服务不可用。用发布事件、历史作业状态、Pod 日志或探针记录核验。 |
| 网关路由配置 | Higress 或 LiteLLM 的路由、后端地址、权重、健康摘除、重试或回退配置导致错误转发或放大影响。用故障时的配置、变更记录和调用日志核验。 |
| 待归类 | 证据不足以确认主类别，或当前两类无法覆盖已观测的故障。在人工确认时说明依据和缺失证据。 |

同一故障链路只列一次，可注明相关类别。例如作业迁移后新地址已可用，而 LiteLLM 仍发往旧地址，主类别为「网关路由配置」，作业迁移作为触发背景。HTTP 500、503、504 是观测结果，同一原因跨状态码或模型时按网关条目口径核对影响，避免重复计数。LiteLLM 计数用作证据，只有可靠关联后才将对应网关条目计入已归因数量。

在 case 开头的「主要原因」中按顺序列出类别、原因、影响时段和条数、关键证据、证据缺口及人工确认状态。其他观察可以留在影响明细或待确认项。

## 保存和验收

先检查 `learning/daily-report/cases/` 是否已有同日同范围的记录，更新对应 case 或新建 `YYYY-MM-DD-5xx.md`。针对单模型的独立 case 可采用 `YYYY-MM-DD-<model-slug>-5xx.md`。

用中文写主要结论、影响范围与分母、关键时间线、证据来源、已观测到的恢复和待确认项。关联日报与同一故障的前后日期 case。对账状态码及合计，检查日期、链接和归因表述。故障数据源查询保持只读，case 只保留排查所需的标识和聚合值。

保存 case 后，将主要原因、类别与尚需核对的证据交给用户或其指定复核人。每项及整个 case 初始标记为「待人工确认」，即使技术证据充分也保留该状态。仅在收到人工明确确认后更新被确认项，并记录确认人、时间和修订意见。部分确认时保留其余项待确认，全部主要原因确认后才将 case 标记为「已人工确认」。
