01 / 组件边界：缓存字节、成员索引与观测信号

Storage 保存和搬运 KV 数据；Events 描述缓存驻留、移除和运行状态。事件不是 KV tensor 本身，路由索引也不是缓存存储。本章按当前源码拆解逻辑块、物理搬运、协调会话和事件传播，再追踪各层可观测信号的产生及导出。

组件职责需要避免的混淆
引擎 KV cache / connector引擎分配 KV、执行 attention，connector 协调 PD cache 传输用 NIXL 不等于使用 Dynamo KVBM
kvbm-logical块状态、哈希、注册、持有/淘汰与池度量逻辑块不等于一段可跨 layout 直接复制的裸地址
kvbm-physical内存/layout 注册、策略选择、搬运与完成通知submit 不等于完成，通知事件不等于 Event Plane 消息
kvbm-engineLeader/Worker、分层 offload、onboarding、对象存储协调不同 backend/feature/配置可能只启用一部分
lib/llm/src/block_manager另一组仍在仓库中的块管理与 KVBM 指标实现不能把这里的字段、端口与新 crates 的指标当成同一套
kvbm-consolidator合并引擎与 KVBM 缓存事件、处理驻留引用并输出兼容事件中间聚合不自动保证持久回放/每消息必达
Runtime Event Plane / KV publisher通用 pub/sub；引擎事件转换、索引入队与外部发布KV routing advisory events 不等于一致性数据库日志

02 / 架构：数据流与元数据流分开

KV 数据Engine G1 GPU ↔ G2 pinned host ↔ G3 disk；G4 object storage 可选。跨实例可先把远端 G3 stage 到远端 G2，再经 NIXL pull 到本地 G2；路径由配置、layout、能力与策略决定。
逻辑/协调SequenceHash / BlockRegistry / pools → Leader 搜索与会话 → Worker / TransferManager → 执行和等待完成 → 目的层注册。
缓存事件Engine 原生 ZMQ 或 KVBM EventsManager → 可选 consolidator / publisher → Event Plane ZMQ/NATS → Router indexer；只传播驻留与负载等元数据。
可观测块池 atomics / legacy counters / pipeline timing logs / relay counters / NIXL telemetry → 对应 Registry 或 exporter → Prometheus/日志平台；OTel propagation 另有明确边界。

4//! RAII guard types that enforce the block lifecycle state machine.
5//!
6//! Every logical block in KVBM progresses through a fixed sequence of
7//! states. The guard types in this module make those transitions explicit
8//! at the type level: each transition consumes one guard and produces the
9//! next. Dropping a guard at any point automatically returns the
10//! underlying slot to the appropriate pool, so blocks are never leaked.
11//!
12//! # State machine
13//!
14//! ```text
15//!                  stage / complete          register_block
16//!   Reset ──────────────────────► Staged ─────────────────► Registered
17//!     ▲                              │                          │
18//!     │          reset               │                          │
19//!     ├──────────────────────────────┘                          │
20//!     │                          drop (reset + return)          │
21//!     └─────────────────────────────────────────────────────────┘
22//! ```
23//!
24//! # Public guard types
25//!
26//! - [`MutableBlock`] — `Reset` state.
27//! - [`CompleteBlock`] — `Staged` state.
28//! - [`ImmutableBlock`] — `Registered` state (cheap-to-clone strong handle).
29//! - [`WeakBlock`] — non-owning reference to a registered block.
30//!
31//! Slot bookkeeping lives in `BlockStore<T>` (`crate::pools::BlockStore`);
32//! `Primary` vs `Duplicate` is captured by an internal flag on
33//! `ImmutableBlockInner` and the corresponding slot state.
01Reset pool 分配 MutableBlock
02写入后 stage/complete 成 CompleteBlock
03注册为 ImmutableBlock / SequenceHash
04强持有阻止回收；Weak 不保活
05释放后按生命周期进入可回收/缓存状态

注册表回答“某逻辑前缀/哈希是否有可持有的块”，池与淘汰后端管理可用 slot 和缓存候选。匹配得到强句柄后，需要保证异步传输期间源、目的内存仍有效；不能只保存一个裸 block ID 后让源被回收。

逻辑块的状态转换不代表 KV bytes 已写入目的地。物理传输成功、目的块注册以及对外发驻留事件之间要保持正确顺序；否则 Router 可能认为一个尚未可用的块已经存在。
