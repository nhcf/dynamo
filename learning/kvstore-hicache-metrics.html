Frontend / Worker 中与 KVStore 相关的指标

场景：Dynamo Worker 接入 SGLang + Mooncake Store，使用 HiCache L3。整理日期：2026-11-06。

Frontend 侧主要看“能否感知共享池，以及路由估计”；Worker 侧主要看“是否实际从 L3 取回/写入，以及本地层间搬运”。

Mooncake Store 的总容量、对象总数、Master RPC 和服务端 GET/PUT 错误还需要采集 Mooncake 自身的监控端点。Dynamo 通用指标不能代替存储服务内部指标。

L1：Worker GPU KV
  ⇅ GPU/Host eviction 与 load_back
L2：Worker host KV
  ⇅ HiCache prefetch（读）与 backup（写）
L3：共享 Mooncake Store
本页是源码支持清单，不是线上已暴露清单。Dynamo 基线：e20c5aa9d44bd6cf8c5827773a14771536341d02；本地 SGLang 基线：2a51479a919142c0012fe2e31d4cae530dcbcad4。实际 runtime 镜像内版本尚未在本次核验；新版本指标、标签和 v1/v2 backend 路径需以实际 /metrics 为准。原始 sglang: 在此前联邦入库中出现为 sglang_。

1. Frontend 暴露的相关指标

下表前四组依赖 --router-mode kv --shared-cache-type hicache 和可用的 Mooncake 对象事件链路；仅配置 Worker 的 --hicache-storage-backend mooncake 不会自动启用 Frontend 共享池感知。一般从 Frontend HTTP 端口（默认 8000）的 /metrics 采集。

指标家族类型 / 单位作用解释边界
dynamo_component_router_shared_cache_hit_rateHistogram，0–1请求 block 中在共享池索引匹配到的比例L3 可复用性估计；是路由时的预测，不是实际 GET 成功率。
dynamo_component_router_shared_cache_beyond_blocksHistogram，blocks共享缓存中超出选中 Worker device overlap 的 block 数量化共享池带来的额外复用机会。

dynamo_router_shared_cache_errors_totalCounter共享缓存查询/订阅错误排查 Mooncake 对象事件流或共享池索引链路异常；不是 Worker PUT/GET 错误计数。

2. Worker 暴露的相关指标

SGLang 原生 sglang:* 由 Dynamo 的 multiprocess registry 回调合并到 Worker 的 DYN_SYSTEM_PORT/metrics（Operator 常用 9090）。需开启 --enable-metrics，并启用 HiCache 和对应 storage backend。Histogram 家族实际包含 _sum、_count、_bucket。

指标家族类型 / 单位作用解释边界
sglang:prefetched_tokens_totalCounter，tokensL3 → L2 的实际载入 tokenHiRadixCache::check_prefetch_progress 在 TP/attention group 取最小完成量、扣掉 host 树已有匹配后计数。反映有效落入 host 的量，不是原始网络全部读取字节，也不保证最终请求全部复用。
sglang:backuped_tokens_totalCounter，tokensL2 → L3 的备份确认 token注意原名为 backuped；不等同于 Mooncake 唯一新增对象/字节数。
sglang:prefetch_pgsHistogram，pages/batchL3 批量读取页数分布_count 是已观察批次数，_sum 是批量页数累计；不是 tokens，换算还涉及 page_size 和布局。
sglang:backup_pgsHistogram，pages/batchL3 批量写入页数分布所查 Mooncake v1 写路径仅对尚不存在的物理 key 发 PUT；该指标不与 backuped_tokens_total 构成简单恒等式。

sglang:cached_tokens_total{cache_source="device"}
sglang:cached_tokens_total{cache_source="host"}		Counter，tokens请求完成后的 L1 / L2 缓存复用可与 storage_mooncake 同图按来源比较；不要将 total 回退序列与各来源序列重复相加。
sglang:cache_hit_rateGauge，0–1引擎采样的整体缓存命中整体趋势指标，不能单独回答 L3 命中率。
sglang:evicted_tokens_total

dynamo_component_gpu_cache_usage_percent
dynamo_component_total_blocks		Gauge，0–1 / blocksDynamo 通用 GPU KV 使用率与总容量仅对应本 Worker 的 GPU KV，0.02=2%；不是 Mooncake Store 的存储使用率。

这些指标的 collector 可能在没有实际 I/O 前没有对应标签序列。storage collector 的标签包括 storage_backend、tp_rank、dp_rank、pp_rank 等；HTTP 请求生命周期的 cached_tokens_total 与 storage collector 的标签集合不同，不能未经匹配直接相除。

3. 如何回答“L3 是否发挥作用”

  1. 先看 storage_backend=mooncake 的 prefetched_tokens_total、backuped_tokens_total 是否有增量，确认实际读写活动。
  2. 再看 cached_tokens_total 的 cache_source，检查是否出现 storage_mooncake，确认请求完成后的 L3 复用归因。prefetch 是载入，cached 是请求复用，两者不可互相替代。
  3. 联看 prefetch_bandwidth、load_back_duration_seconds、Frontend TTFT。命中虽高但载入慢，仍可能不如直接重算；具体应以同负载实测判断。
  4. 如果 Frontend shared-cache 命中与 Worker L3 复用差距大，排查对象事件索引是否完整、TP/PP key 布局是否一致、预取策略、host 空间和实际 GET 失败。
  5. 检查 Mooncake 服务端容量、对象存活与错误。Worker I/O histogram 的 pages 和 bandwidth 按调用记录，不能据此单独证明所有页成功。

当前线上 SGLang 官方文档还提到新版 sglang:storage_prefetch_unfulfilled_tokens_total{reason="host_capacity"}，用于识别 L3 命中却因 host 空间不足不能兑现的 token。本地所查旧提交的 StorageMetricsCollector 没有这一家族，部署前应先核对版本。参考 SGLang HiCache Best Practices。

4. PromQL 模板

# 使用原始 SGLang 名称；联邦入库可能转成 sglang_ 前缀。
# 各查询独立执行。实际筛选还需加入 cluster/namespace/dgd。
# 保留 TP/PP rank，避免把相同逻辑 token 的多个 shard 直接相加。
rate(sglang:prefetched_tokens_total{storage_backend="mooncake"}[5m])
rate(sglang:backuped_tokens_total{storage_backend="mooncake"}[5m])

# 每个 rank 的平均读取批量页数
rate(sglang:prefetch_pgs_sum{storage_backend="mooncake"}[5m])
/ rate(sglang:prefetch_pgs_count{storage_backend="mooncake"}[5m])

# 每个 rank 的按批次平均读取带宽，GB/s
rate(sglang:prefetch_bandwidth_sum{storage_backend="mooncake"}[5m])
/ rate(sglang:prefetch_bandwidth_count{storage_backend="mooncake"}[5m])

# L3 归因复用 token/s；检查实际 cache_source 标签后使用
rate(sglang:cached_tokens_total{cache_source="storage_mooncake"}[5m])

如需算 L3 token 复用占比，分子可用 storage_mooncake 归因 token，分母应来自同一请求群和同一阶段的 prompt token 计数；先验证标签、取消/失败覆盖与 PD 阶段一致。不要将 prefetched_tokens_total / 任何一个全局请求数称为 L3 命中率。未在本次执行线上查询。

5. 容易混淆的指标

  • dynamo_frontend_tokenizer_cache_* 是分词结果缓存，不是 KVStore。
  • dynamo_component_gpu_cache_usage_percent 和 GPU 显存占用不是 Mooncake Store 容量。
  • sglang:kv_transfer_speed_gb_s / sglang:kv_transfer_latency_ms 主要对应 PD 引擎 KV 传输；HiCache L3 用 prefetch/backup 家族。Mooncake Transfer Engine 和 Mooncake Store 也应区分。
  • dynamo_component_image_shared_cache_* 是共享图像缓存，不是 LLM prefix KV Store。
  • Router 的 kv_cache_events_applied 是索引元数据处理；Mooncake KV 数据搬运是另一条链路。

以上定义见 MasterMetricManager 指标注册，Counter/Gauge 类型见 对应头文件。SGLang 主要使用批量调用，优先读 batch 的 request / item / failed item 三种维度；单次 API 路径对应 master_get_replica_list_requests_total、master_put_start_requests_total、master_put_end_requests_total 及各自 failures_total。不要将单次与批量 item 重复求和。

关键语义

  • Master 管理对象和副本元数据；GetReplicaList 找到副本后，Client 仍需搬运数据。应观察“Master 有可用副本 → Worker 预取落入 Host → 请求归因到 storage_mooncake → Frontend TTFT”的趋势，不要求指标数值相等。依据 MasterService 的 GetReplicaList 路径和 Client 数据读取路径。
  • mem_cache_hit_nums_ / mem_cache_nums_ 的分子是累计命中、分母是当前对象数，可以超过 1。官方 calculate_cache_stats 的部分历史 hit-rate 字段就是这种语义，不能显示为 0–100% 的推理缓存命中率。更合适的 Store 查询可用比例是同窗口 rate(valid_get_nums_) / rate(total_get_nums_)，仍不能代替 L3 token 复用率。
  • KEY 存在返回 false 是正常查询结果；ExistKey RPC 错误比例不等于未命中比例。PUT 已存在、部分成功、分配失败也应区分。
  • Master 内存/SSD/文件存储层与 HiCache 的 GPU/Host/L3 是不同分层。只有确实使用该存储介质，才添加 master_nof_allocated_bytes、master_allocated_file_size_bytes 等面板。
  • 同一共享 Store 可能服务多个 DGD，Master 通常没有 Worker 的 model/dynamo_dgd 维度；没有租户隔离或可映射标签时，只做同时间范围的池级趋势对照。HA 场景先区分主备，不把同一个池的容量重复相加。

对照现象与排查方向

  • PutStart 分配失败与驱逐同时增长：优先看容量和 segment 分布。
  • Master 查到副本，但 Worker prefetch 很低：检查 Client/RDMA 错误、host 空间、预取取消策略；“查得到”不保证“取得回”。
  • Worker backup 很高但 keys 净增长小：可能存在已存在 key、覆盖/重复写或驱逐，不必先判定丢数据。
  • Master 容量和 active_clients 同时下降：检查挂载、心跳和客户端存活。

8. 能否用 OTel 串起 Prefill → Mooncake → Decode？

核对日期：2026-11-09。结论：可以通过补充埋点和上下文传播实现；不能仅凭开启 Dynamo/SGLang trace 或部署 OTel Collector，就认定 HiCache L3、Mooncake 数据搬运和 Master 内部全部进入同一 trace。以下是当前两个源码基线的静态分析，尚未在实际镜像或在线流量中验证。

先确认两个不同的数据路径

  • 同一请求 PD 交接：Prefill GPU KV → Mooncake Transfer Engine → Decode GPU KV。使用 Mooncake TE 不要求把 KV 先存入 Mooncake Store，也不要求 Master 位于数据传输路径。
  • HiCache L3 缓存：Worker GPU ↔ Host ↔ Mooncake Store。预取或写回可以发生在 Prefill，也可以由配置支持的 Decode offload 触发；并不是启用 L3 就把每次 P→D 交接改成“P 写 Store、D 读 Store”。

当前源码证据

边界已确认缺口 / 含义
Dynamo → SGLang 请求执行Prefill 和 Decode handler 将 external_trace_header 传入 engine；启用 trace 时来自 Dynamo Context。具备共享请求 Trace ID 的基础，需匹配版本、开启 engine trace 和导出；不自动涵盖所有传输线程。
SGLang PD Mooncake senderMooncakeKVSender::_init_trace_ctx 创建 TraceReqContext，携带 bootstrap_room，module=mooncake；transfer queue 还携带 trace_ctx。此构造没有传 external_trace_header；TraceReqContext::trace_req_start 从该字段提取父上下文。可存在独立传输 trace，不能只因 room 相同就宣称同一条请求 trace。
HiCache → Mooncake Store所读 MooncakeStore::batch_get_v1 / batch_set_v1 包装 Client 调用并记录 pages、bandwidth 等 metrics。这两个方法没有显式 OTel SpanContext 参数或 trace span；本次对 HiRadixCache、CacheController、该 backend scope 的 trace 搜索亦无结果。不能推出 Collector 能补出存储请求 span；不外推为所有新版本、其他 backend 都不支持。
Mooncake Master / 底层 TEMaster 是元数据控制面，传输由 Client/TE 完成。指标可证明活动和错误趋势。本次没有验收实际安装 Mooncake 版本的跨 RPC OTel carrier 和 exporter。SGLang 传输 envelope 不等于 Master 内部 RPC、RDMA task/slice 完整 tracing。

建议的接入工作

  1. 先保证请求面同根。Frontend、Prefill、Decode 配置 Dynamo OTLP 导出；SGLang 同时启用 --enable-trace 和 --otlp-traces-endpoint，核对 engine OTLP 参数采用 host:port 形式。保留 W3C traceparent / tracestate 和采样位；x-request-id 只作辅助标识。
  2. 把上下文带过 scheduler / 进程 / 线程队列。从 Req 的请求上下文显式传入 sender；工作线程重建 Context。D/P 的控制握手或请求载体需传播上下文和 transfer_id。bootstrap_room、rid 只能辅助映射，不能替代 trace_id + parent span id。
  3. 为 PD 增加或修正发送、接收与完成 span。分别观察传输排队、提交、等待与成功/超时/取消；结束时间跟真实完成回执或 poll 状态，不只包住 submit 函数。携带 room、transfer_id、chunk/attempt、rank、bytes 等属性。
  4. 先在 HiCache 侧补 L3 操作 span。为 prefetch / backup 的异步 operation 携带 Context，在实际处理线程中创建 mooncake.store.batch_get / batch_put 的客户端 span，记录落地 token、页数、结果及 backend。这样可以先看整个 L3 调用耗时，即使未改 Master。
  5. 深入 Mooncake 内部时再扩 RPC 与 TE。客户端注入、Master 接收并提取 trace carrier，关联元数据 RPC；Client 和 C++/TE 的异步任务继续携带 span context。自有 RPC 不会因为设置 HTTP trace header 就自动传播。只有这一步完成，才谈 Master/RDMA 子阶段耗时归因。
  6. 批量与缓存复用采用正确因果关系。同请求操作可放在共同 trace 中；多请求合并 batch 用 links 表达多个来源；请求 A 产生、请求 B 命中的共享 KV 应由 B 的读取 link 到 A 的写入，不能永久给一个共享 key 绑定唯一 trace。跨请求 links 需要额外保存 producer SpanContext 的有界映射，现有 block hash 并不自带它。

同一个 trace 内的 Prefill/Decode 可是共同请求父节点下的不同分支，不能为了看起来线性而伪造 parent；实际执行时间也可能重叠。Span Links 用于异步、多来源和跨 trace 因果，见 OTel 官方说明。

验收标准

  • 冷请求与热 L3 请求各保留一条 trace，能识别 cache miss / hit、L3 读取与 host→GPU 阶段；冷请求不应被画成一定发生 L3 GET。
  • 同一推理请求的 Frontend、Prefill、Decode 共享预期的 Trace ID 和父子/links 关系；Mooncake sender 不再出现没有请求关联的独立根。
  • 增加超时、取消、重试与多 rank 验证；span 结束于真实操作终态，传输重试属于同一请求下的新 attempt。
  • 覆盖“一次后台写入、多次后续读取”和“一批多请求”；缓存 key 只使用必要的 hash/摘要，不把 token、key、trace_id 放进 Prometheus 高基数标签。
  • OTel Collector / Tempo 的接收成功只证明传输与存储，最终应检查实际返回的 spans、上下文与因果关系。
