01 / 先明确结论与版本

Planner 是独立容量控制组件。Frontend 负责请求服务，Planner 观察流量和 Worker 状态并调整 Worker 副本，正常推理请求不经过 Planner。二者主要通过 Prometheus 观测和 Worker 成员变化形成反馈，不需要把 Planner 地址配置成 Frontend 的请求下一跳。

本章于 2026-11-03 核对，源码固定于官方代码提交 a908c1a14501b4bb03a7c80833edec0f0e571986，与旧 Planner 教程的 2f296b592 基线分开。分析本地源码和同版本官方仓库文档，未读取实时集群、运行推理或修改部署。

02 / 交互全图：一条请求路径、三条控制链

推理请求Client → Frontend / Router → Prefill、Decode 或 aggregated Worker → Client。Planner 不处在这条同步调用链上。
流量观测Frontend /metrics → Prometheus scrape → Planner PrometheusTrafficProvider → 流量预测与 SLA throughput proposal。
引擎负载Worker/rank FPM → Runtime Event Plane → Planner RuntimeFpmProvider → load proposal / 性能模型。
副本反馈Planner → Kubernetes Connector → DGDSA /scale 或兼容 DGD 写入 → Operator / workload provider → Worker 注册/撤销 → Frontend 发现并更新路由。

Mermaid 交互图源。Frontend 不需要逐请求向 Planner 请示，Planner 的 generate endpoint 也不是推理转发服务。

6. 选策略throughput/latency/load 用 FPM；SLA 明确目标与预测开关、性能模型 warmup
7. 先观察建议advisory:true 时核对建议、诊断、metrics；不会执行容量变更
8. 验证整个闭环决策 → DGDSA/DGD desired → ready Pod → Discovery → Frontend 实际 worker 归因
