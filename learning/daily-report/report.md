## 一期：三个核心指标

### 请求级延迟采集评审

一期要求能按外部请求 ID 复算单次 TTFT、TPOT，每个符合口径的网关流式请求在各项延迟指标中最多计一次，按达到阈值的请求数计算占比。下文的引擎直方图用于对照。SGLang TTFT 直方图能提供引擎侧聚合分位数，输出中保留的是桶计数。SGLang ITL 直方图聚合的是输出间隔，无法关联同一请求的首末输出和 Token 数。vLLM 请求级 TPOT 直方图也只能用于聚合对照。请求明细使用结构化日志或请求事件，并保留统一的外部请求 ID。[SGLang 生产指标](https://github.com/sgl-project/sgl-project.github.io/blob/main/markdown/references/production_metrics.md)

**生产日志抽样。** 从 2026-11-17 北京时间 11:00–23:00 的六条模型路由抽样，按路由与接口最多取 16 条 HTTP 200 日志。117 条中，69 条标记为流式且都有 `ai_log.llm_first_token_duration`，47 条标记为非流式且均无该字段，另 1 条缺响应类型。流式样本中 68 条同时满足首段时间为正、总耗时不小于首段时间且输出 Token 数大于 1。此样本用于确认字段可用性，全日覆盖率需另行统计。[Higress AI Statistics](https://higress.io/en/docs/latest/plugins/ai/api-o11y/ai-statistics/)

| 指标 | 一期使用的 Loki 口径 | 后续可补充的字段 |
|---|---|---|
| TTFT | 按 `request_id` 读取 `ai_log.llm_first_token_duration`，单位毫秒。仓库插件从请求开始计到首次流式响应体回调，作为一期网关 TTFT。 | 网关按协议识别首个携带有效模型输出的事件，并记录相对请求开始的毫秒数。跳过角色、空增量、心跳和 usage 等协议事件。 |
| TPOT | 对符合条件的流式请求计算 `(llm_service_duration - llm_first_token_duration) / (output_token - 1)`，单位毫秒/Token，作为一期网关 TPOT。仓库插件的总耗时结束于流关闭，可能包含 usage 和结束帧。 | 记录首个及末个有效输出事件的时间，用 `(末个输出时间 - 首个输出时间) / (输出 Token 数 - 1)` 计算，每个正常完成且输出至少两个 Token 的请求贡献一次观测。流内多个 Token 合并时，按网关看到的输出事件计时。 |

首轮验证覆盖 Chat Completions 和 Messages、reasoning 输出、空首帧、尾部 usage、异常断流及非流式响应。约定 reasoning 和工具调用如何计入输出时间及 Token 数，并使两者覆盖同一段输出。缺字段、无有效输出和非流式分别统计，延迟样本与总请求量同时展示。后续补采有效输出事件时，用同一请求的客户端流事件和网关日志对照代理缓冲带来的测量差异。日志只提取 ID、模型、时间、Token 计数和终态字段，不保留正文或授权头。

### 一期日报指标和分母

| 指标 | 分子 | 分母 |
|---|---|---|
| 请求可用率 | 有效请求条目数减去 HTTP 5xx 条目数 | 同一模型、同一自然日内的 2xx、3xx、5xx 网关日志条目数，包含流式和非流式。 |
| 429 比率 | 状态码为 429 的匹配日志条目数 | 同模型、同自然日内全部匹配的网关日志条目数。 |
| 流式请求TTFT达成率 | 网关首次流式响应体回调耗时 ≤ 5 秒的有效请求数 | TTFT 有效请求为具有有效首段计时的网关流式请求，按外部请求 ID 去重。 |
| 流式请求TPOT达成率 | 按一期网关计时公式计算的 TPOT 不超过模型阈值的有效请求数 | TPOT 有效请求为 HTTP 2xx、无网关异常标记、具有有效首段和流关闭计时且至少输出两个 Token 的流式请求，按外部请求 ID 去重。 |

日报显示达标数、有效请求数，并在审计明细中列出缺字段的数量。缺少该指标所需的有效计时或 Token 数据的请求，同时从该指标的分子和分母中排除。每项用其有效样本判定，无有效样本时该项暂无法判定。

### 基础 SLA 指标候选：模型推理服务可用性

参考百炼 SLA，建议按模型承诺**自然月服务可用性 ≥ 99.9%**。日报使用同一口径展示前一日的观测值。北京时间按固定 5 分钟窗口计算，每个窗口等权。月度值用自然月窗口汇总，日报每日有 288 个计划窗口。[百炼 SLA 第 1、2 节](https://terms.alicdn.com/legal-agreement/terms/b_end_product_protocol/20250923215800868/20250923215800868.html)

- 有效请求为进入目标模型生产服务范围的推理请求。按外部请求 ID 去除重复日志，排除鉴权失败、参数错误、用户超配额等 HTTP 4xx。首版将 429 单列归因，维持百炼 4xx 口径。
- 失败请求为有效请求中服务侧返回 HTTP 5xx 的请求。能证实因平台故障未能到达服务端的真实请求，在合并证据后同时计入有效请求和失败请求。状态码为 0 的记录单列，按可核实的原因归类。
- 每 5 分钟错误率为失败有效请求数除以有效请求数。参照百炼，已确认采集完整且有效请求少于 5 的窗口按 0% 错误率计算。日志缺失、查询失败或独立探针发现入口故障而无法核实真实受影响请求的窗口标记缺测，正式结果暂无法判定。
- 服务可用性为 `(1 − 各窗口错误率的算术平均值) × 100%`，其中错误率按小数计算。Loki 可以产出已观测请求的可用性，独立入口探针用于补充不可达和低流量时段的故障证据。首版仍沿用外部请求 ID 去重，百炼额外使用账号、窗口、模型及请求参数哈希归并部分失败请求。

此指标衡量平台侧基础可用性。日报的请求可用率按全天有效请求量直接计算，基础服务可用性按 5 分钟窗口等权汇总。TTFT 和 TPOT 衡量流式性能。

### 统计窗口与引擎侧对照

日报支持指定业务日期，默认取前一天。以 `Asia/Shanghai` 构造当天 00:00 和次日 00:00，查询接口使用对应 UTC 时间。Loki 日志查询用 `[start, end)`，按网关请求终态时间归属业务日，验证 Loki 日志时间戳的来源。跨日请求归入终态所在日。Prometheus 兼容接口 `/api/v1/query` 固定以次日 00:00 为求值点，取 `[1d]` 的计数器增量。引擎按观测时间统计，入口与引擎样本量分别展示。[Loki HTTP API](https://grafana.com/docs/loki/latest/reference/loki-http-api/) · [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/)

每个日报模型先按其生产 selector 查询桶和 `_count`。先对每条序列求 `increase` 处理计数器重置，再按核验后的单一采集来源去重、按 `le` 合并各副本桶，最后求 P95。现有看板用 `max by (cluster,service_label_jobname,model_name,pod,endpoint,dp_rank,is_streaming,le)` 消除一组重复序列。日报优先选择唯一抓取来源，采用该去重键前须确认折叠的是同一引擎的重复采集，且保留所有独立副本和 rank。单一来源下，每个模型的查询模板如下。[Prometheus 查询函数](https://prometheus.io/docs/prometheus/latest/querying/functions/)

```promql
histogram_quantile(0.95, sum by (le) (
  increase(sglang:time_to_first_token_seconds_bucket{MODEL_SELECTOR}[1d])
))
sum(increase(sglang:time_to_first_token_seconds_count{MODEL_SELECTOR}[1d]))
```

TPOT 使用经核验的请求级累计直方图及对应计数。Instruct 使用现有看板中的 `vllm:request_time_per_output_token_seconds_{bucket,count}` 作为候选，先核验观测公式及样本范围。该候选仅用于引擎侧对照。现有 SGLang `sglang:inter_token_latency_seconds_{bucket,count}` 用于诊断输出间隔。TPOT 直方图以秒/Token 采集时，将 P95 乘以 1,000。合并前核对桶边界一致、`+Inf` 桶与 `_count` 增量相符。若同一天切换引擎或桶边界，只有在观测定义和桶边界一致时才合并分段增量。保留 `increase` 的原始数值供对账，允许边界外推产生小数。通过生产抓取健康、时间窗样本覆盖和预期服务清单区分缺测与零观测。引擎侧对照暂沿用 TTFT 10 个观测、TPOT 20 个请求观测的下限，首轮对账后复核。采集完整且零观测显示“无样本”，正样本低于下限显示“样本不足”，重要服务缺采或返回异常显示“缺测”。

### 入口请求与终态

复用日志标签 `filename="/var/log/proxy/access.log"`、`authority="i-nhi.zhejianglab.org"` 和映射表中的 `route_name`，沿用 `^/maas/v1(/.*)?$` 路径边界，再按验收确认的推理接口和方法筛选，排除模型列表、健康检查与验收流量。匹配这七个模型路由和推理接口的 zero2x 请求计入一期统计，日志查询按路由和接口筛选。筛选后仅返回请求 ID、路由、状态码、终态时间与类型、流式标志、首末有效输出相对时间和 Token 数等统计字段。原始授权头、请求体和用户标识不进入日表或发布产物。

以 `/loki/api/v1/query_range` 分时段拉取最少字段，默认按小时串行，触及返回上限时二分时间窗。即使缩至同一时间戳仍触及上限，也要标缺测并记录受影响范围，或按可验证且互斥的日志流进一步拆分。延迟统计以同一可信外部请求 ID 在全日去重，使用入口最终一条有效记录。LiteLLM 重试或回退尝试用于归因。缺 ID、终态冲突或解析异常单列计数，无法核对的模型标记数据不完整。用同一固定时间窗的状态码聚合与去重前日志行数对账。

请求可用率为 `1 − 5xx 条目数 ÷ 有效请求条目数`，基于同模型的全天计数。有效请求取 2xx、3xx、5xx。4xx 和状态码 0 等未归类记录分别留在状态明细。429 独立明细以全部匹配日志为分母，按 429 条目数从多到少列出有 429 的模型。查询成功且没有有效请求时，请求可用率标记“暂无法判定”。请求可用率沿用日报目标 ≥ 99.5%，与流式 TTFT、TPOT 一起进入综合判定。网关不可达由独立探针覆盖。

## 二期：故障诊断与优化

| 辅助项 | 来源与用途 |
|---|---|
| 入口探测可用率 | 从网关外每 5 分钟经正式域名对各模型发起一次短推理，分别计成功、失败、缺测窗口。发现网关不可达和夜间无流量故障，与生产请求分开统计。生产输入长度不可识别时，1,024 Token 探针可提供独立的 TTFT 参考。 |
| 延迟与排队 | 在一期指标上增加排队趋势和按输入长度分组，按时段对照。 |
| 错误归因 | 按请求 ID 关联 LiteLLM 日志、数据库中的部署映射和 usage，解释重试、跨模型回退、容量拒绝和用户超额。 |

**按模型选择优化动作。** 以下为待验证的方案。先用异常时段的请求和副本数据确认原因，再选择一项改动灰度验证。

| 一期指标异常 | 如何定位 | 优化动作与验证重点 |
|---|---|---|
| 网关请求可用率下降 | 按错误原因和实际后端拆分失败数。检查是否集中在单个副本，或多个健康副本同时排队并发生容量拒绝。 | 单副本故障时摘除异常路由，待真实推理探测通过后恢复；容量不足时试增副本。对照同负载下的请求可用率和 5xx 数量，同时检查异常断流和重试次数。 |
| 网关 TTFT 阈值内占比下降 | 按输入长度、并发和副本比较排队情况。若只有全量达标占比下降，先检查长输入占比是否增加。 | 同长度请求持续排队且副本负载不均时，调整路由分配；若短请求受长输入阻塞，灰度试行长短请求分流。分别核对两组 TTFT，并观察 TPOT 与请求可用率。 |
| 网关 TPOT 阈值内占比下降 | 在相同输出长度和并发下，用 ITL 趋势检查输出间隔变长是否与长输入 prefill 或单副本高负载同步。 | 若长 prefill 干扰解码，在支持的部署上试调 prefill 分块大小；若单副本并发过高，试将部分流量分给有余量的副本。核对 TPOT、TTFT 和总输出吞吐，避免以排队或吞吐损失换取单项改善。 |

**效果验收。** 选一个模型，用同版本、同硬件的对照组与灰度组承接可比流量，或回放同一批请求。记录并发、输入/输出长度分布、样本量及改动前后三项核心指标。试验前约定改善目标和可接受的吞吐、资源开销；目标达成且其余指标在约定范围内再推广，超限则回退。日报仅在发生变更时附一行“模型｜改动｜对照值→灰度值｜推广或回退”。

**官方参考。** 可用性与延迟分列、按模型和服务档位考核，可参考 [OpenAI Scale Tier](https://openai.com/api-scale-tier/) 和 [Google Gemini 在线推理 SLA](https://cloud.google.com/vertex-ai/generative-ai/sla)。有效请求、失败及统计窗口参考[阿里百炼模型推理 SLA](https://terms.alicdn.com/legal-agreement/terms/b_end_product_protocol/20250923215800868/20250923215800868.html)。限流归因参考[无问芯穹调用规则](https://docs.infini-ai.com/gen-studio/api/usage-and-billing/billing.html)和[智谱并发权益](https://docs.bigmodel.cn/cn/guide/platform/equity-explain)。一期承诺阈值见上表。

## 日报展示：一份日表，三个出口

### 本机定时任务

本机 cron 每天北京时间 08:00 和 09:30 分别运行 [定时发布入口](publish_daily_report.py)的预发和正式阶段。预发调用 [run_report.py](run_report.py) 生成前一完整自然日的日报，加入数据洞察后上传。正式阶段校验同日期预发回执和 HTML 摘要，再上传同一份含数据洞察的 HTML。生成脚本只读查询 Higress Loki，按外部请求 ID 去重，计算请求可用率、429 比率及 TTFT、TPOT 阈值内占比。每个日期输出 `YYYY-MM-DD/index.html`，汇总数据内联。整天查询和页面校验通过后才替换同日文件。请求可用率的日报目标为 ≥ 99.5%。流式延迟按一期网关计时口径判定。

手动补跑可指定业务日期。以下命令从仓库根目录执行。

```bash
python3 learning/daily-report/run_report.py --date 2026-11-17
```

预发和正式版的数据洞察包括5xx 条目最多的模型和主要状态码、两项延迟超阈值贡献最大的模型，以及可比指标较前一日的最大百分点变化。缺少前一日数据时页面提示无法对比。

定时任务使用本地锁避免重叠，运行日志和发布回执位于 `~/.local/state/dynamo-sla/`。两套环境的凭据从本机用户专用配置读取。匹配七个模型的 zero2x 请求纳入定时统计。

### 正式发布流程

1. **调度与取数。** 每天北京时间 08:00 生成并校验前一自然日的日报后发布预发，09:30 将经过预发校验的同一份含数据洞察的日报发布正式环境。支持指定日期补跑。首轮通过 Grafana 对照同一固定区间的查询结果，随后由任务使用只读身份调用已授权的数据源接口。分别记录查询耗时、返回状态、日志覆盖和抓取覆盖。
2. **生成日表。** 以 `(business_date, model_id)` 为行键，保存窗口、映射和口径版本、生成时间、修订号。页面页首展示统计区间。每行包括按状态码统计的网关日志计数、请求可用率与 429 比率，两项延迟阈值内占比、各自达标数、分母、不可测数量及列级状态。保存查询模板版本和异常摘要，便于回溯。校验恰好七行、空值与状态一致、计数可对账。每次从同一已校验快照生成 HTML 与通知摘要。
3. **发布网页。** 本地先用固定样例和历史日表渲染，核对七行排序、单位、分子/分母、缺测原因和更新时间。上线后按业务日期发布至智算开放服务平台报表广场的指定区块，页面提供历史日报入口，并可链接到对应时间范围的 Grafana 看板。原稿记录的上传工具 `zjic-report-upload` 指向另一台机器，本工作区无法读取其说明。联调前取得可运行入口、区块标识、日期更新约定和发布身份，并验证返回的 `viewUrl` 可由预期读者访问。
4. **发送摘要与补发。** 网页发布成功并可读后，钉钉与邮件引用该次 `viewUrl`，展示异常模型、缺测项和核心指标摘要。用业务日期和内容修订号记录发布结果与各渠道发送结果。同日期重复运行时，内容一致则复用发布记录，内容有变化则更新同一日期条目。部分渠道失败时仅重试失败渠道。预发检查发现缺测时发布带明确标记的日报并告警。迟到数据进入后重算受影响日期，生成新修订并标注更新时间。以首周实测的日志迟到分布确定自动回补时段。

## 实施顺序与上线验收

| 步骤 | 实施与通过条件 |
|---|---|
| 1. 确认生产映射 | 补齐七个模型的生产选择器与路由。确认同一路由是否承载多个对外模型，必要时加经验证的请求模型字段。验证匹配目标路由的 zero2x 请求纳入统计。测试环境、相似路径及同名非目标服务均应被排除。 |
| 2. 对账请求可用率和 429 比率 | 逐模型复算 2xx、3xx、5xx 的有效请求数与 5xx 数，再用全部匹配日志复算 429 比率。验证状态码 0、重复日志、跨日、分页和无有效样本的表现。 |
| 3. 对账网关流式延迟 | 通过同一请求对照网关日志与客户端流事件，验证首段与流关闭计时、请求去重、单 Token 请求的排除和 reasoning Token 计数。在一个完整业务日复算七个模型的两项达标数、分母和不可测数量，含恰好等于阈值的样例。 |
| 4. 联调日报网页 | 用同一日表驱动网页、钉钉与邮件，逐项核对值和更新时间。验证发布失败、单渠道失败、同日重复执行、迟到数据修订与历史链接。面板与网页使用各自读者权限。 |
| 5. 验证二期诊断 | 在验收环境模拟入口不可达和探针停跑，分别产生失败与缺测窗口。抽取一次排队或重试事件，按模型、时间和请求记录定位对应后端。 |
