ACK Request Plane Trace：链路走查

本页回答两件事：一棵请求 trace 应该长什么样，以及在查询界面上怎么找到它、抓不到时怎么判。对象仍是 nhss-job / dynamo-qwen38-27b-mixed-demo（Frontend、prefill、decode、aggregated 各一副本，Worker TP=4，Request Plane=tcp）。span 的来源、源码行号与三级保证程度见 链路设计，执行顺序与验收命令见 工作清单；本页引用的保证程度与该设计文档一致，不另立标准。

编制日期：2026-10-29 · 部署快照：2026-10-28 · 本文为走查文档，未连接集群、未修改资源；下文时间戳均为示意值，不是现场采集数据。

1. 读图约定（先读这一节再看用例）

  • 缩进表示父子，与设计 §2 的主链一致：generate → handle_payload(client) → handle_payload(server) → engine.generate。同一缩进深度的并列子树之间只按时间先后排序，不要仅凭缩进推断它们是父子。
  • 每行后标注三项：所在角色（frontend / prefill / decode / aggregated）、span 名、保证程度（稳定 / 需核实 / 仅 1.7.0）。低于“稳定”的 span 在 1.4.1 私有镜像上可能根本不产生。
  • lifecycle 阶段是旁挂的语义层。request.dispatch、worker.operation.prefill 等挂在请求 future 上，用来标注阶段归属，不代替传输层的父子边。同名 span 在 Frontend 与 Worker 两侧都可能出现，靠 dynamo.component 与 dynamo.instance.id 区分。
  • 外部父节点不显示是正常的。客户端只用 traceparent 注入一个外部 parent，自身并不产生 span；界面里最顶层 span 没有父节点，不等于断链。
  • handle_payload 有同名两份：Frontend 出口侧是 client（otel.kind 为 client 语义），Worker 入口侧带 otel.kind = "server"。看到两个同名的要按 kind 分辨，不要当成重复上报。
  • P/D 之间不是父子关系。prefill 与 decode 是两个独立执行体，它们与前驱之间用 OTel Link 关联（设计 §4）。只看父子边会得出“decode 没有来源”的错误结论。

2. 用例 A：PD 请求（prefill + decode）

先在 Frontend 生成一次请求，路由到 prefill 完成首段计算，再由 decode 继续出 token。两条 Worker 子树共享同一个 Trace ID 与同一个 dynamo.request.id；第二次派发（去 decode）与 prefill 子树的先后关系用时间戳判断，不要强行画成一条单链。

trace 4bf9…4736   request_id=…   model=Qwen3.8-27B      （t+ 为示意值）
t+0ms    ├─ completions                   frontend     需核实
t+0ms    │  └─ generate                   frontend     稳定      request_id, model
t+2ms    │     ├─ handle_payload(client)  frontend     稳定      traceparent 在此注入
t+3ms    │     │  └─ handle_payload(srv)  prefill      稳定      otel.kind=server
t+3ms    │     │     ├─ request.dispatch  prefill      仅 1.7.0
t+3ms    │     │     ├─ worker.admission  prefill      仅 1.7.0
t+4ms    │     │     ├─ worker.operation  prefill      仅 1.7.0
t+4ms    │     │     │  └─ worker.operation.prefill    仅 1.7.0
t+4ms    │     │     └─ engine.generate   prefill      稳定      disagg_role=prefill, ttft_ms
t+310ms  │     │        ── prefill 结束；KV 经 NIXL 转到 decode，该传输不在主链路 span 内 ──
t+312ms  │     ├─ handle_payload(client)  frontend     稳定      第二次派发：选到 decode
t+313ms  │     │  └─ handle_payload(srv)  decode       稳定      otel.kind=server
t+313ms  │     │     ├─ request.dispatch  decode       仅 1.7.0
t+314ms  │     │     ├─ worker.operation  decode       仅 1.7.0
t+314ms  │     │     │  └─ worker.operation.decode     仅 1.7.0
t+314ms  │     │     └─ engine.generate   decode       稳定      disagg_role=decode, output_tokens
t+2.4s   │     └─ response.streaming      frontend     仅 1.7.0  SSE 回传边界
t+2.4s   └─ (客户端收到 last chunk)

要点：

  • 两个 engine.generate 是判断 P/D 分工的唯一稳定锚点：它们的 disagg_role 分别是 prefill 与 decode，属性里带 ttft_ms、output_tokens、itl_p50/p99/max_ms 等。TTFT 应落在 prefill 段的结束处，而不是 decode 段的开头。
  • decode 的 engine.generate 上会有一条指向前驱的 Link，指向 prefill 侧上下文；Link 在多数查询界面上不画成边，需展开 span 详情查看 References。找不到 Link 时可能是前驱上下文缺失触发的 trace 级告警（worker_trace_link），先确认日志级别再判定实现缺失。
  • worker.operation.prefill / .decode 的耗时是 runtime 边界，不等于引擎内部 prefill/decode 执行时间。要引擎级数字看 engine.generate 属性或引擎自身 span。
  • response.streaming 只有一个，出现在 Frontend 侧；按设计 §3 它属于 frontend 组件，不要到 Worker 上找。

3. 用例 B：aggregated 请求

路由到 aggregated 副本时，只有一条 Worker 子树，没有 P/D 的第二次派发，也没有跨机 KV 传输。这是最简单的形态，适合用来先确认采集链路本身通了，再去排 PD。

trace 9d2c…1a07   request_id=…   model=Qwen3.8-27B      （t+ 为示意值）
t+0ms    ├─ completions                         frontend     需核实
t+0ms    │  └─ generate                         frontend     稳定
t+1ms    │     ├─ handle_payload(client)        frontend     稳定
t+2ms    │     │  └─ handle_payload(srv)        aggregated   稳定      otel.kind=server
t+2ms    │     │     ├─ request.dispatch        aggregated   仅 1.7.0
t+2ms    │     │     ├─ worker.admission        aggregated   仅 1.7.0
t+3ms    │     │     ├─ worker.operation        aggregated   仅 1.7.0
t+3ms    │     │     │  ├─ worker.operation.prefill   aggregated   仅 1.7.0   首段
t+3ms    │     │     │  └─ worker.operation.decode    aggregated   仅 1.7.0   续段
t+3ms    │     │     └─ engine.generate         aggregated   稳定      disagg_role=aggregated
t+1.9s   │     └─ response.streaming            frontend     仅 1.7.0
t+1.9s   └─ (客户端收到 last chunk)

判读方式：这条链上不出现 decode 副本的名字就是正常结果；如果出现了，说明路由把请求派到了别的副本，与 trace 无关，应回到部署记录核对副本与标签。aggregated 场景下 worker.operation.prefill 与 .decode 可能同时存在，因为它们描述的是同一进程内的两个阶段，不是两台机器。

4. 用例 C：取消与错误

设计 §2 #10 约定“取消与错误在响应流式阶段结束 span”。这一类请求最容易被误判成“链路断了”，需要按下面的形态读，而不是看 span 是否成对出现。

形态一：客户端主动断开（cancelled）
t+0ms    ├─ completions                 frontend     需核实      以取消结束
t+0ms    │  └─ generate                 frontend     稳定
t+2ms    │     ├─ handle_payload(client) frontend    稳定
t+2ms    │     │  └─ handle_payload(srv) decode      稳定
t+2ms    │     │     └─ engine.generate  decode      稳定      cancelled=true
t+700ms  │     └─ response.streaming     frontend    仅 1.7.0  提前结束，不是等满

形态二：引擎侧报错
t+2ms    │     │     └─ engine.generate  decode      稳定      error_kind=…
（对应请求在 Frontend 侧以错误结束；是否额外产生 response.streaming 视版本而定）

形态三：Worker 侧因传播断链而没有父节点
t+2ms    (独立根 span) handle_payload(srv) decode   稳定      没有 traceparent → 新起 trace
  • 形态一/二是“有 span、有异常属性”：链路完整，结论应写成“请求被取消/失败，耗时至取消点为止”。cancelled、error_kind、finish_reason 三者一起看，不要只看 HTTP 状态码。
  • 取消时 Frontend 侧与 Worker 侧的结束时刻允许不重合：Frontend 在客户端断开时收尾，Worker 要等引擎响应取消。两段时长不同不是错误。
  • 形态三是“真的断链”：Worker 侧出现独立 trace、dynamo.request.id 也与前端不一致，才是传播问题。排查按 §6 的顺序，不要先怀疑采集端。
  • 输出被截断但 finish_reason 为正常值，通常不是 trace 问题，而是上游 max_tokens 或客户端断开时机，属另一类问题。

5. 查询方法

以下假设按 采集参考 起了 Collector 与查询后端，且 环境变量片段 已合入 DGD。Collector 的命名空间与服务名是占位值，执行前替换成平台确认过的实际值。

5.1 打开查询界面

kubectl -n <collector-namespace> port-forward svc/jaeger 16686:16686
# 浏览器打开 http://127.0.0.1:16686

5.2 三种查法，按可靠性排序

查法入口适用注意
Trace ID 直查Search → Trace ID已知 traceparent 的那一次请求；PD 跨副本时最可靠粘贴 traceparent 的第 2 段（32 位十六进制），不要带 00- 前缀与采样位
标签查Search → Tags：dynamo.request.id=…只有业务侧 request id、没有 traceparent 时该属性由 lifecycle 提供；若版本不含 lifecycle，则查不到
服务 + 操作查Service 下拉 + Operation 过滤确认某副本是否在上报；看整体形态Service 名来自 OTEL_SERVICE_NAME，必须与 DGD 实际值一致

按 Service 过滤时，四个副本的服务名由环境变量片段提供，形如 dynamo-qwen38-27b-frontend、-prefill、-decode、-aggregated。这些名字是本机候选值，未经集群核实；若下拉里的名字与之一致，说明该副本的 env 已生效。

常用 Operation 过滤值：generate（Frontend 派发边界）、engine.generate（引擎调用边界）、handle_payload（传输层两侧）、request.lifecycle（lifecycle 根）。

5.3 界面上的局限，先知道再看图

  • Jaeger 的图只画父子边，不画 Link。PD 的 prefill↔decode 关联要靠 Trace ID + 时间戳 + dynamo.request.id 手工对照，或在 span 详情的 References 里找 Link。
  • “没有父节点”≠ 断链。外部客户端只注入 traceparent，不产生 span，顶层无父属正常（用例 A/B 的 completions 行）。
  • 时间轴按 span 起止时间排，不按上报时间。跨副本时钟偏差过大时，P/D 的先后会看起来错乱；此时以 dynamo.request.id 与 dynamo.process.epoch 判定归属，不要用肉眼排序下结论。

5.4 区分“没产生”与“没入库”

采集参考里的 Collector 配置带了一个 debug exporter。用它可以快速把两类失败分开：

kubectl -n <collector-namespace> logs deploy/otel-collector --tail=200 | grep -E 'Trace ID|span'
# 有 span 输出 → 已发送，问题在后端存储或查询条件
# 无 span 输出 → 应用侧没有产生，回到 §6 判定顺序

若连 Collector 日志都没有，先确认 Collector 是否在跑、Service 端口是否为 4317、应用侧 OTEL_EXPORTER_OTLP_TRACES_ENDPOINT 指向的是 otel-collector:4317 而不是 Worker 的 :9090 或 NIXL 的 19090——后两者不是 OTLP 目标。

6. 抓不到时怎么判

顺序不能乱：先判断是级别过滤还是版本缺失，再判断是传播断链。乱序排查最常见的后果是把“版本里没有这个 span”当成“采集没配好”，然后反复改环境变量。

  1. 该 span 在版本里是否存在——对照 链路设计 §2 的保证程度。标“仅 1.7.0”的阶段在 1.4.1 私有镜像上不产生，这是预期，不是故障。取证方式是工作清单 T01 的包版本与 --help。
  2. 日志级别是否放行——handler span 由 #[tracing::instrument] 展开，级别不足则 span 根本不创建，其子 span 会直接挂到上一层。表现为“少了一层”而不是“整条没有”。responses 为 debug、connection_monitor 为 trace，其余多为 info。
  3. 采样是否丢弃——三处必须对齐：上游是否透传 sampled=01、Dynamo 侧 OTEL_TRACES_SAMPLE_RATIO、Collector/后端采样。任一处丢弃都会造成“看起来断链”。联调期统一设 1.0。
  4. 传播是否断开——tokio::spawn 未使用 in_current_span() 会丢当前 span，Worker 侧会另起一个根。表现为用例 C 的形态三。
  5. Collector 是否拒收——看 debug exporter 有无输出、看 Collector 自身日志里是否有拒绝或队列溢出。到这一步才动采集端配置。
三个高频误判：① 顶层没有父节点——外部客户端本来就不产生 span；② handle_payload 出现两次——client 与 server 同名不同 kind；③ decode 找不到来源——P/D 之间是 Link 而非父子。三条都在 §1 有对应说明。
