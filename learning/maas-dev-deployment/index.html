06 / 版本边界和配置差异

事实应如何理解
Operator 运行版本 1.4.1；本地教程基线为 1.7.0 workspace此前源码中的 OTLP metrics、FPM、Frontend 统计等能力需按实际运行镜像重新验证。
DGD/DCD/ScalingAdapter CRD 同时 served v1alpha1 和 v1beta1；storage 仍是 v1alpha1Operator 最近 INFO 日志内反复出现 v1alpha1 deprecation warning；这是弃用提示，不是已证实 reconcile 失败。
CRD 标签无法直接确定 release仅凭 API 形状不能断定 CRD 来源或不兼容；更新前应核对 Operator、CRD、Chart 组合。
Worker Monitor generation=4；当前含 system-0/system-1与部分新教程形态相似，也不能据此认定 Operator 二进制是新版。以镜像 digest 为准。
NATS Label 2.11.1，镜像与 /varz 2.10.21运行版本优先于 Chart appVersion 标签；computed image 与 Pod 一致。

07 / 下一步实施与验收顺序

优先级工作验收标准
P0先确认 maas-dev 当前是否只作为平台预置；若需推理实战，选定一个模型与实际 runtime 镜像版本出现对应 DGD/DCD/Frontend/Worker，能关联部署声明、镜像 digest 和模型服务。
P1确认 ARMS 是否消费 Dynamo Monitor，并验证抓取身份 /metrics 权限在实际采集后台找到 Operator target UP，并查到该版本真实存在的指标。
P1明确应用指标采用 ARMS PodMonitor 或 Collector Prometheus receiver；防止重复采集有流量后看到 Frontend/Worker/引擎序列，标签能关联模型、部署和 Pod。
P1补齐日志、Trace Collector 路由和部署端变量，遵循实际 runtime 版本能力请求 ID / Trace ID 可关联到前端和 Worker；不能只验收 Collector Running。
P2补齐 Grove 与 NATS 遥测；按需要设计 NATS PVC 和副本策略观测端点与采集格式匹配；若需持久化，单独验证重建后状态。
P2核对 CRD/Operator/Chart 版本组合与弃用 API 迁移方案不依据当前源码直接升级或修改 CRD storage。

以上是分析后的实施建议，本次均未执行配置修改、部署新模型或升级。NATS 持久化与控制面 API 迁移应在有具体工作负载和恢复要求后再确定方案。
