Dynamo Prometheus Metrics
分类、作用与使用场景

整理日期：2026-11-04 · 当前仓库提交 e20c5aa9d44bd6cf8c5827773a14771536341d02 · 按此前 Dashboard 主体组件整理，并补充 Storage & Events / Operator 等模块。

版本和指标归属先于指标名字。

本页以当前仓库的官方 Metrics Catalog 为主，关键语义结合源码核对。此前部署文档记录 runtime/operator 为 1.4.1，未在本次重新连集群确认镜像。标为当前仓库能力的指标不能视为线上已存在。本次不调整线上采集和 Dashboard。

Dynamo 自有 dynamo_*、引擎原生指标、NIXL exporter、DCGM、抓取系统指标应分层使用。前面线上验证的事实来自 2026-11-03：Frontend/Worker/Planner 指标已有入库，SGLang 入库前缀为 sglang_，GPU 为 DCGM；未据此推断其他扩展模块已采集。

专题：Frontend / Worker 的 Mooncake + HiCache L3 KVStore 指标 →

按问题选择观测点

TTFT 上升，GPU 不忙

Frontend 阶段 / tokenize → event loop / Tokio → Router queue / overhead → Request Plane → Worker permit / admission。

不要直接扩 GPU；先找到请求停留的阶段。

TTFT 上升，PD 传输排队

Prefill/Decode 角色负载 → bootstrap/transfer queue → 引擎 KV latency → NIXL 字节、时延与错误。

Engine transfer、NIXL transfer 和用户 TTFT 是不同时间边界。

KV 命中率下降

Tokenizer 缓存与 GPU KV 分开 → Router 估计 → 选中 Worker → 引擎复用 → 发布/订阅/索引事件。

缓存热度下降与事件丢失可能表现相似，必须联看。

Planner 不扩容

输入 signal / observed/FPM → load 与 throughput 决策原因 → 插件结果/约束 → predicted → Ready 副本与 Operator reconcile。

不要只看预测 0 或 SLA gauge；先确认信号可用。

流式响应中断

Frontend cancellation / migration / failures → Worker errors / cancellation → response plane → Pod/控制面事件。

客户端取消、服务故障、响应面背压要区分。

up 正常但请求失败

model_ready / Worker inventory → generate 端点 errors → engine health → Router 可用集合。

采集健康与业务 readiness 分层判断。

指标类型与查询方式

  • Counter：累计事件或量，通常用 rate / increase；先 rate 再聚合以正确处理各进程重启。
  • Gauge：当前值、最近样本或估计；可以升降，通常直接展示。名称带 total 不保证为 Counter，例如部分 LoRA churn 是逐步 Gauge；以 # TYPE 和实现为准。
  • Histogram：家族展开为 _bucket / _sum / _count。均值先分别汇总分子分母再除；分位数先汇总 bucket，并保留 le。
  • Enum：Prometheus 中常展开为一组 one-hot Gauge；同名状态 label 才是原因，数值 1 表示当前活跃状态。

采集出口与标签边界

  • Frontend：通常 HTTP :8000/metrics，内嵌 Router 与 Runtime 指标同出口。KServe gRPC 模式另有端口和指标覆盖差异。
  • Worker / standalone Router / KV State Agent：DYN_SYSTEM_PORT/metrics；默认可禁用，Operator 通常为 9090，CLI 示例常见 8081。端口不同不是指标语义不同。
  • Planner：独立 metric_reporting_prometheus_port / PLANNER_PROMETHEUS_PORT；Operator 通常 9085。Standalone Indexer 使用自身 HTTP --port。
  • Operator：独立 ServiceMonitor；业务 Frontend/Worker 通常由 PodMonitor 或组织现有 collector 采集。此前 ack-LB 采用的联邦入库方式不能直接套用默认 Helm 假设。
  • 标签：dynamo_namespace 是逻辑命名空间，namespace 是 Kubernetes namespace；dynamo_endpoint 是 RPC，endpoint 可能是抓取端口或 HTTP API 语义，需按家族核对。component / worker_type / phase / request_phase 也不是同一维度。
  • 采集补充：cluster、dynamo_dgd、pod 等通常由采集链路补充，并非所有官方原始端点自带。Frontend 的本地指标和 Planner 也不会自动拥有所有 runtime hierarchy 标签。
  • 聚合：先确定 model、role、pod、worker_id、dp_rank 和统计时段；多 Frontend 观察同一 Worker 可重复，多 TP rank 指标也可能重复。业务请求、路由 attempt、PD 两腿及内部 RPC 不能直接相加当用户请求数。

模板采用前面 ack-LB 入库中已使用的部署标签。两行查询代表两条独立面板 target，不能整段作为单条表达式执行。新增指标需要先确认镜像版本与 /metrics；本次没有对新增模板重新执行线上查询。

比例 0–1 在 Grafana 使用 percentunit；Frontend seconds、Planner ms、NIXL 微秒、GB/s 与 tokens/s 分开设单位。无请求时 0/0、无序列或缺少必要信号都不能补成“正常 0 延迟”。时延与命中率应同时显示观察样本数。

历史 KVBM、FPM 与分布式 Trace 的边界

  • KVBM：当前官方 Catalog 说明在 v1.7.0 移除；此前 Storage & Events 源码教程固定在旧提交，涉及 kvbm_*、offload/onboard、host/disk/object 等家族，应只用于对应旧版能力。不能把当前 HEAD 的指标目录与旧版 KVBM 清单拼成同一个版本的全集。
  • FPM：forward-pass 数据是引擎执行反馈，经事件通道供 Router / Planner 使用。Planner 的 engine_queued_* 等只是部分投影；FPM 持久化 JSONL、OTel span、Prometheus Gauge 不应混为同一种数据出口。
  • NIXL：独立 exporter 和配置，不能认为 Worker :9090/metrics 已自动包含其指标。当前 Dynamo 文档与最新 NIXL main 对多进程 exporter 的机制有版本差异，部署时需按镜像中实际 NIXL 版本确认端口和聚合方式。不要把上游新指标清单当作 1.4.1 runtime 的验收标准。
  • 可观测覆盖：Prometheus 用于聚合趋势与告警；逐请求的 PD 调用、KV 传输耗时及跨组件因果仍需 trace / 事件记录。具有传输 metrics 不证明 Request Plane 与 Storage & Events 已完成全链路 trace 关联。
